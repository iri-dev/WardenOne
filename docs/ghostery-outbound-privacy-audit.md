# G-06 outbound privacy contract

Phase 06 checks what leaves WardenOne and what remains after data erasure. It adds no reporting service or provider lookup. The source-derived inventory is `docs/outbound-destinations.json`; `tools/build-outbound-inventory.js --check` and `tools/test-outbound-inventory.js` keep it aligned with shipped JavaScript and the configured feed inventory. The inventory classifies 30 literal contact hosts and five dynamic destination classes. `tools/test-privacy-disclosure.js` separately compares runtime destinations with `PRIVACY.md` and `permissions.html`.

## Browser observations

On 28 October 2026, `tools/browser-outbound-privacy.js` ran against Edge 150.0.4078.48 in a disposable profile. With optional reputation switches disabled and automatic list updates suppressed for the bounded observation, CDP recorded **zero external service-worker requests** during three seconds of synthetic ordinary browsing. The page contacted only the controlled fixture site and tracker. A tracker-learner observation stayed in local storage, and a history entry omitted the URL query and fragment. This proves the observed case, not the absence of every possible future request; startup list updates, popup checks, Script Drift and page features have their separate triggers in the inventory.

The same native run exercised the actual worker configuration and request construction while intercepting `fetch` before any provider call left the browser. Every tested provider was silent with its switch off; key-dependent checks were silent without a key. Enabling one switch at a time produced only the expected host. The 15 cases covered Safe Browsing, PhishTank, OpenPhish's public list, AbuseIPDB, urlhaus, WhoisXML age, domain reputation and threat intelligence, automated VirusTotal URL and hash checks, and user-started VirusTotal, breach, domain-age and Pwned Passwords checks. WhoisXML domain reputation also invokes its age endpoint, so that case recorded two hosts. All automatic URL reputation cases excluded the synthetic query, fragment and credentials. The automated VirusTotal URL ID decoded to the sanitized scheme, host and path; its hash path contained only a SHA-256. The manual VirusTotal check stayed silent without a saved key and sent the selected URL with its automatic switch off. User-started breach and RDAP checks sent the registrable domain; Pwned Passwords sent a five-character SHA-1 prefix.

The request-shape limit matters: automatic URL reputation keeps the **path**. A secret embedded in a path can therefore reach an enabled provider. The manual VirusTotal URL scanner sends the user-selected URL, including any embedded query or credentials. `PRIVACY.md` discloses both boundaries. Page-owned resource fetches and on-by-default script/download re-fetches are dynamic destinations; they are inventoried separately from provider requests and may carry the resource address. The native provider harness intercepted requests and did not contact those services.

## Deletion and retention

The outbound browser run confirmed a 31-day-old Activity item was absent from the `history-get` result while a fresh item remained. `tools/browser-history-modes.js` covered normal, browser-session and no-saved-history modes, pending-write revocation, redaction, and restart cleanup. `tools/browser-privacy-site-erase.js` verified target-site records and shared caches removed while unrelated site data and global configuration survived, including a full browser restart. `tools/browser-privacy-erase.js` verified 18 seeded data sets removed, with no recovered API key or UI DOM cache after restart. `tools/browser-uninstall-privacy.js` removed the extension and reinstalled the same unpacked path and ID in the same profile; seeded history, key, session record and popup DOM marker were inaccessible after reinstall.

The first site-erase run (`tmp/ghostery-phase06/site-erase.log`) exposed a real failure: the erase lock rejected its own configuration-pruning write. `background.js` now permits only the erase operation's private symbol token through that lock; ordinary writes remain blocked. `tools/test-privacy-erase-write.js` and the repeated native site-erase run cover this boundary. The popup erasure harnesses also wait for the replacement worker to become ready before checking the result.

## Disclosure and limits

`PRIVACY.md` describes local learner/history state, provider switches and data shapes, list and build checks, page re-fetches, retention, erasure and uninstall. `permissions.html` names the external hosts and feature triggers. The inventory contains no WardenOne-owned reporting endpoint. Literal host classification, source/policy parity and the bounded native trace support the no-developer-telemetry claim for the tested behavior. They cannot establish that every future browsing path has no outbound traffic, and the extension's documented feed and page-feature requests still occur under their stated conditions.

The accepted native artifacts are under ignored `tmp/ghostery-phase06/`: `outbound-verified-02.json`, `site-erase-fixed-02.log`, `full-erase-fixed-02.log`, `history-modes.log` and `uninstall-preflight.json`. `docs/ghostery-outbound-privacy-evidence.json` records their hashes alongside the relevant source and disclosure files. The maintainability gate result is recorded there too.
